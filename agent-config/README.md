# Checkout-local agent configuration

A normal clone contains every selected instruction and skill dependency. Claude
uses the generated `.claude/skills` projection and `@AGENTS.md`; Codex uses the
canonical `.agents/skills`. No global skill installer, setup hook, network fetch
or personal MCP configuration is needed to load these workflows.

## Ownership

| Material | Authored source | Consumer treatment |
| --- | --- | --- |
| Common prompt rules | `agent-config/rules/` in dev-skills | Generated AGENTS section |
| Shared workflows and assets | `skills/` in dev-skills | Pinned generated `.agents/skills` files |
| Repository-specific workflows | Consumer `.agents/skills/<name>/` | Repo-owned canonical source |
| Claude discovery copies | Canonical skills above | Generated regular files |
| Generator and update/check workflow | `agent-config/` in dev-skills | Pinned generated consumer tooling |
| Repository invariants and Claude mechanics | Consumer AGENTS/CLAUDE outside managed block | Repo-owned, retained by sync |

The five common procedures describe operations and outcomes without native tool
names. Their relative dependency on `harness-operations` includes one capability
adapter and conditional Claude/Codex references automatically. Repo skills own
only their fixtures, acceptance gates, domain procedures and local policy deltas.
`check-content.mjs` keeps native tool assumptions out of selected common prose;
actual capability/discovery behavior still needs runtime evidence.

Physical discovery copies are generated artifacts, not additional authored
sources. CI compares them with the exact pinned upstream and rejects changes,
missing/extra assets, name collisions, stale local projections and altered managed
prompts. Local checks work offline; upstream verification adds provenance proof.

## Consumer configuration

The checked-in `.agents/manifest.json` declares schema 1, source repository
`onsager-ai/dev-skills`, a full immutable `source.revision`, and arrays named
`skills`, `rules` and `local_skills`. Relative cross-skill links close the dependency
set automatically. Complete skill directories, references and binary assets are
preserved. Source symlinks and references escaping the skill tree are rejected.
The generated lock records the resolved dependency set and file/rule checksums.

For ordinary work, just use the repo. To check drift locally:

```sh
node .agents/sync.mjs --check
```

To author a local skill, edit its canonical `.agents/skills` source, then regenerate
with a dev-skills checkout containing the pinned revision. To change shared
behavior, edit dev-skills; consumers do not fork generated bodies. A maintainer
can change selections and regenerate explicitly:

```sh
node .agents/sync.mjs --source /path/to/dev-skills --revision <full-commit-sha>
node .agents/sync.mjs --check --source /path/to/dev-skills
```

For initial onboarding, run `agent-config/sync.mjs` from the source checkout with
`--repo /path/to/consumer --source /path/to/dev-skills`. The consumer needs a
manifest, regular AGENTS/CLAUDE files and its declared canonical local skills.
Generation refuses to discard edited managed files; restore those changes or
review them upstream before regenerating. Commit the complete generated result.
Node 22 and Git are maintainer/CI prerequisites, not agent-session setup steps.

## Updates without developer setup

The generated workflow verifies every PR against the source SHA using the trusted
upstream checker. A weekly schedule and manual dispatch fetch current dev-skills
main, regenerate and verify the selected subset, and propose a draft update PR.
Existing PRs for that revision are reused by skipping duplicate proposals. The
workflow never merges or installs into a developer profile.

It uses the consumer's built-in Actions token with contents/PR write permission;
no custom secret is required. GitHub must allow Actions to create PRs for this
repository/organization. If that setting is disabled, drift checks still work
and updates can be generated by an authorized agent or maintainer. GitHub does
not trigger extra PR workflows for this token: the updater runs its drift checks
before opening the draft, and required product CI must be triggered through the
repository's supported process before merge. The schedule becomes active only
when its workflow is on the default branch and the generator exists on upstream
main; merge the dev-skills source before adopting consumers pinned to it.

Current automation proposes updates for the selected source revision; it does not
silently advance a consumer's effective policy. Target harness discovery,
Cloud/offline/cache validation and organization merge gates still apply.
